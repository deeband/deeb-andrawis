How to Avoid / Minimize Automated Test Maintenance

Written at Shield34 · QA Automation

A test suite that's expensive to maintain gets neglected, then ignored, then deleted. These are the structural habits I rely on to keep a Selenium suite cheap to maintain as the product underneath it keeps changing.

1. Page Object Model

  • POM is easy, reliable, readable and reusable.
  • When the UI changes, you edit one class representing that component — instead of editing the ten tests that use that page.
  • Separate locators, actions on elements, and the test itself.
  • Tests get shorter because they reuse POMs and their methods.

2. Wrappers

  • Use a wrapper for every component, so that when more than one element shares a locator, they're less likely to collide.
  • This is easy and reusable with an abstract POM — for example, two popups that share a wrapper but have different child-element locators.

3. Waits

  • Use waits wisely — explicit waits beat implicit waits.
  • Avoid Thread.sleep(). It's sometimes "enough," but when the application slows down, a fixed sleep isn't — an explicit wait is far more efficient.

4. Locators

  • Avoid depending on information that's likely to change, such as locating elements by visible text.
  • Start with id — short, fast, safe and unique.
  • Then className, name, tagName, linkText.
  • XPath and CSS should be the last options — they're the least reliable.

5. Automation locators

Add automation-only locators that UI developers know not to touch — for example, aut-click-btn. If a UI developer changes a class name, the automation locator stays untouched and the UI tests aren't affected.

6. Strings

  • Avoid hardcoded strings in automation tests.
  • Where possible, pull strings from the same place UI developers get them, so a copy change elsewhere doesn't silently break a test.
  • Keep strings in variables so an update only has to happen in one place.

7. Make your code generic

Build POMs and tests to be generic and reusable. Reuse common classes and methods, and avoid duplicating code.

Communication matters

Finally: when there's a UI change coming, the automation developer should be the first to know, so they can adapt the tests ahead of time. That communication between UI developers and automation developers is what avoids flaky failures and the investigation time that follows them.
