Reduce Selenium Flaky Tests — What You Should Know

Written at Shield34 · QA Automation

Selenium changed the game for countless software companies and became a critical piece of agile development. But Selenium isn't flawless, and one of its most common hurdles is recurring flaky tests. They're so common that they don't just hurt a company's bottom line — they create "test result blindness" that erodes quality and frustrates testers.

Flaky tests slow testers down because they have to constantly distinguish between a real bug and a false positive. Here are the concrete practices I've relied on to cut flakiness down.

Waits

  • Use waits wisely — explicit waits are far more reliable than implicit waits.
  • Avoid Thread.sleep().
  • Avoid driver.manage().timeouts().implicitlyWait(X, TimeUnit.SECONDS).

Locators

  • Start with id — short, fast, safe and unique.
  • Then try className.
  • Then name, tagName, linkText, etc.
  • XPath and CSS selectors should be the last resort — they're the least reliable.
  • Avoid locators that are likely to change.

Automation locators

  • Add dedicated automation locators so UI developers won't accidentally break them — for example, aut-click-btn.
  • That way, if a UI developer changes a class name, they know to leave the aut- prefixed locator untouched.

Strings

  • Avoid hardcoded strings in automation tests.
  • Where possible, pull strings from the same source the UI developers use — for example, from the i18n file — so a copy change doesn't silently break your tests.

Second run

If a run ends with, say, 20 failures, automatically generate a new run containing only those failed tests. That gives you a focused run of 20 tests, which usually surfaces which failures were genuinely flaky.

Environment

  • Keep tuning machine resources until you find the CPU/RAM sweet spot for running your tests without slowness problems.
  • Restart the machine when you notice it's starting to affect test runs.
  • Size the number of machines to match the number of tests.

Threads

  • Keep tuning the number of parallel threads until you find an optimal number — too many threads can itself cause slowness.
  • Make the thread count configurable so it can scale with your test suite.

Summary

Flaky Selenium tests are a real pain, but they're a solvable one — and there's a large community of Selenium engineers sharing what works. The practices above are the ones that made the biggest difference for me day to day.
