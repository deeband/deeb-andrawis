How to Reduce Flaky Tests

Written at Shield34 · QA Automation · 3 min read

Flaky tests are one of the most expensive problems in test automation — not because any single failure is hard to fix, but because they erode trust in the whole suite. This is the playbook I use to get flakiness down to a manageable level, finishing with a retry mechanism built on TestNG.

Key takeaway

A retry should mask noise, not bugs. Cap retries at 1, reset test state between attempts, and log every test that needed a retry so the real failure doesn't go uninvestigated.

Environment

  • Keep tuning machine resources until you reach the ideal CPU/RAM for running your tests without slowness problems.
  • Machine resources should be editable and sized to the number of tests.
  • Restart the machine when you notice it's affecting your tests.

Waits

  • Use waits wisely — explicit waits beat implicit waits.
  • Avoid Thread.sleep().
  • Avoid driver.manage().timeouts().implicitlyWait(10, TimeUnit.SECONDS).

Locators

  • Avoid depending on information that's likely to change.
  • Start with id — short, fast, safe and unique.
  • Then className.
  • Then name, tagName, linkText.
  • XPath and CSS should be the last options — they're the least reliable.

Automation locators

Add automation-only locators that UI developers know not to touch. If a UI developer changes a class name, the automation locator stays untouched and the UI tests stay unaffected.

Strings

Avoid hardcoded strings in automation tests. Where possible, read strings from the same source UI developers use, so a copy change doesn't silently break a test.

Independent tests

Tests shouldn't depend on each other. A failure in one test — say, a popup that didn't get closed — shouldn't cascade into failing unrelated tests.

Test retry mechanism

Retrying a test only when it fails is one of the most effective flakiness reducers, with a few caveats:

  • Make sure the retry isn't affected by the state the first failure left behind — for example, close a lingering popup, or redirect to the test's starting URL before retrying.
  • Set the retry count to 1. If a test doesn't pass twice, the odds of it passing a third time are low — more retries just hide a real problem.
  • Track tests that fail on the first attempt but pass on retry, and investigate the root cause instead of letting the retry paper over it.

In TestNG, this means implementing IRetryAnalyzer, so each failed test gets one retry:

public class RetryAnalyzer implements IRetryAnalyzer {
    private int retryCount = 0;
    private static final int MAX_RETRY_COUNT = 1;

    @Override
    public boolean retry(ITestResult result) {
        if (retryCount < MAX_RETRY_COUNT) {
            retryCount++;
            // Reset any state the failed attempt left behind
            // before TestNG runs the test again.
            return true;
        }
        return false;
    }
}

Then an IAnnotationTransformer wires that analyzer onto every @Test automatically, so nobody has to remember to add it method by method:

public class RetryTransformer implements IAnnotationTransformer {
    @Override
    public void transform(ITestAnnotation annotation, Class testClass,
                           Constructor testConstructor, Method testMethod) {
        annotation.setRetryAnalyzer(RetryAnalyzer.class);
    }
}

Finally, register the transformer as a listener in your suite XML:

<listeners>
    <listener class-name="com.example.RetryTransformer" />
</listeners>

Second run

If a run ends with 20 failures, generate a new XML containing only the failed classes (or, better, only the failed tests rather than whole classes). That focused rerun of 20 tests will usually show you which failures were genuinely flaky.
